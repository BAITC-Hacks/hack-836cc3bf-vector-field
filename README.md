# HackAlem — объяснимая приоритизация финансовой сети

Инструмент для AML-аналитика: определить, кого проверить первым среди участников наблюдаемой транзакционной сети, и проверить основания на графе.

**Текущий статус:** подготовлены материалы кейса, аудит данных и план реализации. Продуктовый pipeline, роли, три финальных CSV, API и интерфейс ещё не реализованы. Команды запуска продукта будут добавлены по факту реализации.

## С чего начать команде

**Обновление: осталось 4,5 часа.** Текущий тайминг — `docs/EXECUTION_PLAN_270_MIN.md`. Контракт v1 и общие примеры уже записаны: `docs/API_CONTRACT.md`, `shared/contracts.ts`, `shared/fixtures.json`. HTTP/Pydantic реализация ещё не выполнена. Старый agent-first plan из `context/` больше не является рабочим расписанием.

1. Прочитать `AGENTS.md` — инструкции для coding agents и обязательные инварианты.
2. Прочитать `docs/BUILD_BRIEF.md` — актуальный scope, правила, контракты, задачи команды и gates.

## Что строим

```text
Parquet → метрики → роли / кластеры / приоритеты → CSV + snapshot
                                                     ↓
                                      список → граф → карточка
                                                     ↑
                                        один Investigator
```

Сначала объяснимая аналитика и экран. AI подключается к готовым read-only функциям. Работа ядра не зависит от LLM API.

## Ограничения

Выборка охватывает внутрибанковские переводы ≥5000 KZT за июль 2026, собранные исходящим обходом до 4 колен от 81 seed. Входящая сторона неполна; глубина 4 обрезана; нет остатков, атрибутов клиентов и размеченных ролей. Все выводы — гипотезы для проверки, score — эвристика, а не вероятность виновности. GID в браузерных/API контрактах передавать строками.

Формальные стартовые критерии ролей, приоритет, evidence, rubric и план масштабирования до ~1 млн узлов находятся в `docs/BUILD_BRIEF.md`. После реализации README должен отражать фактически применённые версии правил и точные команды запуска.

## 1. Контекст задачи и границы продукта

Известные seed — отправная точка расследования. Они не являются размеченной обучающей выборкой для классификации всех остальных клиентов. Наличие пути от seed не доказывает противоправную деятельность связанного клиента.

Аналитик получает три файла с уже собранной сетью. Наш продукт не подключается к банковским системам, не расширяет фактический охват данных и не устанавливает личности клиентов. Он рассчитывает структурные признаки и помогает выбрать, куда направить ограниченное время проверки.

Основные вопросы:

1. Где сходятся переводы от нескольких участников?
2. Какие узлы распределяют средства и связывают участки сети?
3. Какой объект имеет смысл проверить следующим и почему?
4. Какие наблюдаемые факты поддерживают гипотезу и какие данные отсутствуют?

Результат — рабочая аналитическая гипотеза с проверяемыми основаниями. Он не является решением о блокировке, юридическим выводом или вероятностью преступления.

## 3. Входные данные и проверенные особенности

| Файл | Одна строка | Поля | Размер |
|---|---|---|---|
| `nodes.parquet` | Клиент, включая изолированные seed | `gid,depth,is_seed` | 2248 |
| `edges.parquet` | Агрегированная направленная пара за период | `src,dst,sum_kzt,n_tx,depth` | 3119 |
| `transactions.parquet` | Отдельный перевод без уникального transaction_id | `src,dst,date,sum_kzt` | 4840 |

По коленам: 81 / 472 / 462 / 789 / 444 узла. Наблюдаемый оборот — 365 890 012.01 KZT. Суммы и количество транзакций сходятся с edges. Полный граф включает 35 слабосвязных компонент: 16 с рёбрами и 19 изолированных seed. Крупнейшие компоненты содержат 1877 и 270 узлов.

Особенности, которые должны определять поведение продукта:

- **Все gid превышают безопасную целочисленную точность JavaScript.** В API, tools и React они передаются строками, в CSV — полными десятичными целыми.
- **444 узла depth=4 не имеют исходящих из-за границы обхода.** Отсутствие выхода не даёт оснований назвать их terminal.
- **У 335 non-seed наблюдаемый выход больше входа.** Ограничение inflow нельзя применять только к seed.
- **31 seed без исходящих:** 19 изолятов и 12 только получателей. Все должны находиться поиском и присутствовать в результатах.
- **97 строк transactions повторяют четыре исходных поля.** Это не доказанные ошибочные дубли: без tx_id их сохраняем.
- **Даты имеют точность до дня.** Нельзя утверждать, что перевод утром предшествовал другому вечером.
- **Порог ≥5000 KZT и один банк.** Ненаблюдаемые переводы, остатки, наличные операции и деятельность клиента не достраиваются моделью.

## 4. Договорённость о ролях и score

| Поле | Что означает | Чего не означает |
|---|---|---|
| `role` | Основная гипотеза о функции узла в наблюдаемой сети | Юридический статус клиента |
| `role_score` | Эвристическая уверенность по правилам и доступным признакам | Откалиброванная вероятность истинной роли |
| `priority_score` | Приоритет дальнейшей проверки в текущем деле | Вероятность преступления |
| `cluster_id` | Принадлежность к рассчитанному сообществу | Установленная преступная группа |
| `limitations` | Что ограничивает конкретный вывод | Декоративный общий disclaimer |

Шесть ролей: consolidator — схождение переводов; distributor — веерный выход; transit — признаки прохождения потока; terminal — кандидат в конечного получателя в наблюдаемом окне; coordinator — структурный посредник; peripheral — достаточных признаков заданных ролей не выявлено.

Сначала применяются условия допуска роли, затем рассчитываются сигналы и score. Если несколько ролей совместимы, в CSV остаётся одна основная, а карточка показывает вторичные признаки. Если данных недостаточно, fallback peripheral сопровождается низким score и явным объяснением неопределённости. Это не означает, что клиент безопасен.

Точные формулы v0, пороги, множители и tie-breaking приведены в `docs/BUILD_BRIEF.md`. Это предлагаемый baseline: после изменения правила обновляются config/version и документация, а все узлы пересчитываются. Нельзя делать исключение по gid для красивого демо.

## 5. Обязательные выходные схемы

### nodes_roles.csv

| Колонка | Тип | Условие |
|---|---|---|
| gid | int64 | Каждый исходный gid ровно один раз |
| role | string | Одна из шести предусмотренных ролей |
| role_score | float | Конечное значение от 0 до 1 |
| cluster_id | integer | Существующий кластер |
| priority_score | float | Конечное значение от 0 до 1 |
| evidence | string | Непустое объяснение с числами, ≤200 символов |

Дополнительные колонки разрешены, обязательные нельзя переименовать. Формат идентификатора должен переживать запись и повторное чтение без округления.

### clusters.csv

`cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis`

Каждый узел входит ровно в один кластер. Изоляты учитываются отдельно. Внутренний оборот считается по исходным направленным рёбрам с обоими концами внутри кластера, каждое ребро один раз. `top_gids` — до трёх gid через `;`; hypothesis — объяснимая гипотеза из наблюдаемых признаков.

### top_nodes.csv

`rank,gid,role,priority_score,why`

Минимум 20 уникальных узлов. Rank начинается с 1. Сортировка: priority по убыванию, при равенстве gid по возрастанию. Поля согласованы с nodes_roles. Why объясняет приоритет, а не просто повторяет название роли.

## 6. Архитектура и жизненный цикл данных

```text
Исходные файлы (не изменяем)
    ↓ проверка схем, ключей, сумм и количеств
Направленный граф со всеми узлами
    ↓ признаки + компоненты + сообщества
Версионированные правила ролей и приоритета
    ↓ объяснения + ограничения + summaries
Три CSV и единый snapshot
    ├── API → priority list / graph / dossier
    └── read-only tools → Investigator → проверка ссылок → UI
```

Pipeline работает batch-режимом. API загружает результаты и обслуживает запросы к ним. Клик по узлу и вызов tool не запускают весь пересчёт. Frontend отображает серверные показатели, даже когда показывает только часть графа.

Для MVP достаточно pandas/NetworkX, FastAPI/Pydantic и React/Vite. Графовая БД, RAG, отдельное хранилище векторов, orchestration engine и обучение ML не входят в scope. Один Investigator не является обязательной зависимостью аналитического CLI.

Версия snapshot должна связывать исходные hashes, версию правил и параметры кластеризации. Это позволяет проверить, что карточка, CSV и AI-ответ относятся к одному расчёту.

## 7. Интерфейс и основной пользовательский сценарий

Первый экран сразу показывает период, размер выборки, главные ограничения и очередь проверки. Основное действие — выбрать узел из очереди или найти его по точному gid.

После выбора:

1. Карточка показывает роль, priority, role_score, cluster и наблюдаемые вход/выход.
2. Граф показывает направленное окружение выбранного узла.
3. Evidence объясняет конкретные признаки и позволяет посмотреть соответствующие связи.
4. Limitations указывают, что нельзя заключить из этой выборки.
5. Next check предлагает конкретные недостающие данные.

По умолчанию используется ego-граф, не облако всех 2248 узлов. Ограниченная выборка соседей помечается: видно общее число и сколько скрыто. Поиск по gid работает по полному snapshot, включая изоляты и скрытые фильтром узлы. Стрелки обозначают реальные исходящие переводы; визуальная позиция узла не является доказательством иерархии.

Роль кодируется цветом и текстом, seed — отдельным знаком, depth=4 — предупреждением. Нельзя передавать важный смысл только цветом. Граф должен быть полезен и без AI.

## 8. Предлагаемый API и согласование контрактов

Это спецификация интерфейса, а не список уже работающих routes. Типы и fixtures v1 находятся в shared/, точная семантика и ошибки — в docs/API_CONTRACT.md. Runtime-схемы реализует backend-владелец по этому контракту. При расхождении краткого описания здесь и transport v1 использовать v1.

| Route | Назначение |
|---|---|
| `GET /api/summary` | Размеры, период, ограничения, top nodes и версия расчёта |
| `GET /api/entities` | Список всей сети с фильтрами и pagination |
| `GET /api/entities/{gid}` | Полный профиль узла с evidence |
| `GET /api/subgraph?gid=...&hops=1&limit=80` | Ограниченное окружение с направленными рёбрами |
| `GET /api/clusters` | Сводки рассчитанных кластеров |
| `GET /api/export/{filename}` | Скачивание одного из трёх разрешённых CSV |
| `POST /api/investigate` | Опциональный запрос к Investigator |

Обязательные договорённости: gid/src/dst — строки; scores — числа; даты — ISO; отсутствие значения — null; NaN/Infinity запрещены. Пустое окружение изолята — валидный результат. Неизвестный gid — понятный 404. Урезанный подграф возвращает `truncated` и `omitted_count`.

До параллельной интеграции нужны fixtures для обычного узла, изолята, depth=4, урезанного подграфа и ошибки AI. Нурасыл определяет семантику, Даулет реализует схемы, Аки и agent-владелец используют те же имена полей. Изменение контракта синхронизируется между всеми потребителями.

## 9. Роль Investigator

Один агент отвечает на уточняющие вопросы над готовой аналитикой. Пример: «Кто является общим получателем выбранных seed и почему его стоит проверить?»

Инструменты: `get_entity_profile`, `get_subgraph`, `find_common_recipients`, `rank_entities`. Они используют тот же snapshot и не позволяют агенту менять роли, score или исходные данные.

Ответ содержит findings, ссылки на evidence и gid, ограничения и next checks. Числа лучше отображать из фактов backend, а не заново формулировать моделью. Backend проверяет существование ссылок и согласованность фактов. Проверка JSON-схемы не доказывает истинность свободного текста.

Начальная граница исполнения — не более 6 tool calls, глубина ≤4, ограниченные результаты и общий timeout. Показанная в UI activity соответствует реальным вызовам. При отсутствии ключа или ошибке LLM карточки, поиск, граф и экспорты продолжают работать. Replay, если добавлен, явно обозначается как предыдущий результат.

## 10. Команда и три ветки

| Ветка | Владелец | Область работы | Первый результат |
|---|---|---|---|
| `codex/frontend` | Аки | `frontend/` | Один экран на согласованном fixture: список, граф, карточка |
| `codex/backend` | Даулет | `pipeline/`, `backend/`, runtime-схемы | Пересчёт, три валидных CSV, snapshot и API |
| `codex/agent` | Нурасыл | `agent/`, методология и AI | Зафиксированные правила/evidence, затем один Investigator |

`main` — общая интеграционная база. Ветки создаются от одного коммита с материалами и документацией. Они локальные, пока явно не выполнен push. Создание веток не запускает агентов и не создаёт отдельные рабочие каталоги.

На собственном клоне участник переключается командой, соответствующей своей роли:

```text
git switch codex/frontend
git switch codex/backend
git switch codex/agent
```

Это три альтернативы, не последовательность для одного участника. Если ветка опубликована только на remote, сначала `git fetch origin`, затем создать tracking branch для своей ветки. Не запускать несколько coding agents, одновременно переключающих ветки в одном рабочем каталоге: использовать разные клоны или worktree.

В конце рабочего блока: проверить свой результат, commit, синхронизировать изменения с командой и интегрировать через Даулета при изменениях между слоями. Shared contract меняется первым, затем producer и consumers. Нельзя подменять несовместимость временным переименованием поля только на frontend.

## 12. Приоритеты и контроль времени

Первая работающая цепочка: сырые данные → расчёты → CSV → реальный список → карточка и связи. Если она не работает, новые агенты, screens и stretch-функции не начинаются.

Последовательность усиления: data traps и evidence → поиск любого gid → воспроизводимость → один Investigator → одна полезная temporal/trace функция при запасе. Brief и next check сначала делаются шаблонами из рассчитанных признаков.

Ритм команды — короткие рабочие блоки с проверкой контрактов и общего flow. Последние 90 минут зарезервированы под freeze, чистый запуск, документацию, репетицию и сдачу. Если времени меньше, режется scope, а не обязательные результаты.

## 13. Проверки и критерии готовности

- [ ] Все 2248 исходных gid представлены ровно один раз, включая 19 изолятов.
- [ ] Согласованы ключи, суммы и n_tx между transactions и edges.
- [ ] ID проходят Python → JSON → browser → API без изменения.
- [ ] Роли допустимы; scores конечны и в [0,1]; evidence числовой и ≤200 символов.
- [ ] Каждый cluster_id существует; суммы размеров кластеров и seed совпадают с исходными.
- [ ] Top содержит ≥20 уникальных gid, правильную сортировку и объяснение приоритета.
- [ ] Нет automatic terminal по depth=4 или обвинительных выводов по centrality.
- [ ] Один запуск создаёт три CSV за <5 минут без LLM key и ручных шагов.
- [ ] Повторный запуск с теми же данными/config даёт те же аналитические результаты.
- [ ] Любой gid, изолят и узел из небольшой компоненты находятся в UI.
- [ ] AI failure не ломает основной экран и экспорты.
- [ ] README содержит реально проверенные команды, версии и ограничения.
- [ ] Есть схема решения, второй laptop run и репетиция 5-минутного демо.

Без ground truth не публикуем accuracy/F1. Проверяем смысловые инварианты, объяснимость случайных узлов и чувствительность top-list к настройкам. Выполненные проверки фиксируются владельцами, а не предполагаются по наличию тестовых файлов.

## 15. Сценарий демо и развитие

Показ: запуск и размер сети → fan-in кандидат → распределитель из другой компоненты → depth=4 с честным ограничением → один AI-вопрос, если готов → поиск произвольного gid и экспорт. Реальные примеры для рассказа находятся в RED_TEAM_REVIEW; результат для них всё равно рассчитывается общими правилами.

Для ~1 млн узлов потребуется пересмотреть хранение и вычисления: columnar preprocessing, компактный graph backend, приближённая/локальная betweenness, пакетные сообщества и выдача только небольших подграфов в UI. Точную betweenness текущего прототипа не обещать для такого масштаба. Реализация масштабирования не входит в пятичасовой MVP.

Финальное обещание продукта: **«От известных участников — к объяснимой очереди проверки финансовой сети».**
