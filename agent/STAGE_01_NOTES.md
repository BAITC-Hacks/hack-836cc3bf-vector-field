# NURASYL-01 — методология и граница Investigator

Статус: проверена методология v0 по `docs/BUILD_BRIEF.md` и `docs/DECISIONS.md`; подготовлена **только** read-only граница tools на синтетических fixtures. Живой Investigator и расследование по Parquet ещё не реализованы.

## Проверка правил по реальному аудиту

Источник чисел — `analysis/dataset_audit.json`, который получен из исходных Parquet. Это исследовательские метрики, а не рассчитанные роли или ground truth.

- Все 2248 gid больше безопасного целого JavaScript. В tools и JSON оставляем десятичные строки. 19 seed изолированы; правило `peripheral` с `isolated_seed` не объявляет их безопасными. В полном графе 35 компонент, включая изоляты.
- 444 узла depth=4 имеют нулевой outflow из-за границы обхода. Условие допуска роли предшествует score: `terminal` на них запрещён, но наблюдаемый fan-in всё ещё может поддержать `consolidator`.
- Узел `100000003684369100`: 24 разных входящих gid, 62 исходящих, 58 входящих и 67 исходящих транзакций, наблюдаемый `out/in≈2.23`. Возможны одновременно сигналы `consolidator` и `distributor`; `transit` по текущему ratio не допускается. Правило основного role и `secondary_roles` покрывает смешанный профиль без нового enum.
- Узел `100000008603629100`: non-seed, 19 входящих, 61 исходящий, `out/in≈2.74`. В аудите 335 non-seed с наблюдаемым outflow больше inflow. Это следствие неполного входа, а не самостоятельная аномалия или доказанный баланс. `outflow_exceeds_observed_inflow` остаётся ограничением наблюдения.
- Узел `100000002398779100`: 13 входящих gid, один исходящий, 1 095 690 KZT входа и 66 000 KZT выхода. Fan-in поддерживает гипотезу консолидации; из отношения потоков нельзя заключать, что остаток удержан. Для допуска `terminal` отдельно нужны даты входов и ограничение конца периода, которых профиль аудита не показывает.

Критических противоречий в зафиксированной v0-методологии по этим профилям не найдено. Positive midrank использует все положительные значения признака во всём snapshot, одинаково обрабатывает ties и не создаёт искусственный максимум в малой локальной группе. `role_score` остаётся эвристической силой роли, `priority_score` — отдельной суммой шести вкладов. Доля межкластерного incident volume относится к сообществам внутри слабосвязной компоненты; coordinator не означает управление людьми.

**Интеграционный пробел:** `CommonRecipientsResponse` содержит пути, но не содержит `Evidence`/`evidence_id`. Текущий validator поэтому не пропускает finding о пути без отдельного доверенного fact. На следующем этапе service adapter должен детерминированно оформить путь как существующий `Evidence` shape с указанием `path_not_money_provenance`, либо Investigator должен использовать common result только для навигации и запрашивать подтверждающие profile/edge facts. Общий transport v1 здесь не менялся.

## Что сделано в `agent/`

- `boundary.py`: async Protocol четырёх tools, точные аргументы и общие пределы из `docs/API_CONTRACT.md`. Будущий live provider должен делегировать в тот же in-process snapshot service, что API.
- `fixture_provider.py`: явно синтетический provider. Возвращает только поддержанные примеры из `shared/fixtures.json`; для неизвестного gid — `EntityNotFound`, для известного gid без полной fixture-карточки — `FixtureUnavailable`. Не рассчитывает роли, score или пути заново.
- `validation.py`: проверяет текущий `meta/snapshot_id`, известные gid, разрешение ссылок, точное совпадение фактов с выполненными tools, реальные записи вызовов и сохранение ограничений. Цифры в свободном тексте finding запрещены: приложение должно отображать их из проверенных facts. Проверка ссылок и формы **не доказывает смысл остальных фраз**; непроверяемый вывод нужно удалить или вернуть `failed`, а не показывать как `completed`.
- `INVESTIGATOR_INSTRUCTIONS.md`: минимальные рамки для будущего одного model loop.

## Подключение на следующем этапе

От Даулета нужны: live service provider с четырьмя операциями поверх **того же** snapshot, `snapshot_id` от hashes данных/config, полный `Entity.evidence` включая шесть `priority_component_*`, `role_signal_strength` и `role_support_multiplier`, полный набор gid для validator, фактический журнал вызовов. Для путей нужен доверенный evidence-факт или явно ограниченный ответ без finding о движении средств.

API/model loop, timeout исполнения модели и frontend-панель не входят в этот этап. При отсутствии готовых CSV работа над AI не должна блокировать обязательное ядро.

Проверка: `python -m unittest discover -s agent -p 'test_*.py' -v` — 8 тестов без API key.
