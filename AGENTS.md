# HackAlem: инструкции для coding agents

## Задача и приоритет источников

Мы строим объяснимый инструмент приоритизации узлов финансовой сети для AML-аналитика. Пользователь должен увидеть, кого проверить первым, почему, какие связи это подтверждают и чего пока нельзя заключить.

Порядок источников истины:
1. Официальный кейс в `case/` и его фиксированные схемы CSV.
2. Реальные Parquet-файлы и результаты воспроизводимых проверок.
3. `docs/BUILD_BRIEF.md` — актуальный scope, контракты и распределение работы.
4. Этот файл — правила реализации.
5. Документы `context/` — исторический контекст. Их agent-first milestones, HumanGate, SQLite и multi-agent defaults НЕ являются текущими требованиями.

Не расширять scope самостоятельно. Не превращать проект в transaction monitoring, AML chatbot или полноценный case management.

Перед реализацией scoring/UI explanations прочитать `docs/DECISIONS.md`: positive midrank определён в BUILD_BRIEF; priority раскладывается на шесть числовых evidence facts; роль и priority объясняются отдельно; coordinator в UI — «Структурный посредник (кандидат)», enum остаётся coordinator. Не переносить из внешних review недоказанные независимость плательщиков, управление сетью и соединение разных weak components.

**Актуальное уточнение:** transport v1 фиксируется в `docs/API_CONTRACT.md` и `shared/contracts.ts`, примеры в `shared/fixtures.json`. Эти файлы уточняют названия/формы полей из BUILD_BRIEF; CSV-схемы официального кейса не меняются. Рабочее расписание на оставшиеся 270 минут — `docs/EXECUTION_PLAN_270_MIN.md`. Прежде чем писать собственные схемы, прочитать v1. Fixtures синтетические; не использовать их scores как результаты анализа.

## Обязательный результат

- Один локальный запуск: три исходных Parquet → расчёты → три заполненных CSV, менее 5 минут после установки зависимостей.
- `nodes_roles.csv`: все 2248 исходных узлов, включая 19 изолированных seed.
- Колонки: `gid,role,role_score,cluster_id,priority_score,evidence`.
- Роли: `consolidator,transit,distributor,terminal,coordinator,peripheral`.
- Оба score конечные, в диапазоне [0,1]. Evidence непустой, содержит числа, не более 200 символов.
- `clusters.csv`: `cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis`.
- `top_nodes.csv`: `rank,gid,role,priority_score,why`, минимум 20 уникальных узлов, по убыванию priority; одинаковый score разрешать сортировкой по gid.
- Экран: топ-лист, направленный граф, роли/кластеры, поиск произвольного gid, карточка с объяснением.
- README: реальные команды запуска, правила и пороги ролей, ограничения, масштабирование до ~1 млн узлов.
- Схема решения и сценарий 5-минутного демо с 2–3 узлами.

Не хардкодить роли, кластеры, приоритеты или топ-лист по конкретным gid. Известные примеры допустимы только в документации и тестовых ожиданиях отдельных метрик.

## Архитектура

`Parquet → deterministic analytics → CSV + JSON snapshot → FastAPI → React`

`Investigator → read-only tools над тем же snapshot → проверенные ссылки на evidence`

- Python, pandas, NetworkX; FastAPI/Pydantic; React/Vite. Использовать существующий стек, если реализация уже началась.
- Расчёты ролей, score, кластеров и числового evidence принадлежат Python, а не LLM или frontend.
- CLI не импортирует AI-зависимости и не требует API key.
- Один Investigator после работающего аналитического ядра. SDK — тонкая оболочка, не причина добавлять orchestration.
- Без PostgreSQL, Neo4j, vector DB, RAG, собственной ML-модели, внешнего enrichment, auth, workflow engine и deployment в MVP.
- Достаточно файлов и памяти процесса. Не вводить persistence без конкретной необходимости.
- Аналитика не пересчитывается при каждом клике или вопросе агенту.

## Критические правила данных

- `gid/src/dst` в Python/Parquet — int64. В HTTP JSON, tool inputs/outputs и React — десятичные СТРОКИ. Это касается также `top_gids`, путей, списков соседей и ключей графа. Никогда не применять JS `Number`, `parseInt` или unary `+` к gid.
- CSV сохраняет полный десятичный идентификатор без округления и scientific notation.
- Сначала добавить в граф ВСЕ nodes, затем edges. Полный граф: 35 слабосвязных компонент, из них 16 с рёбрами и 19 изолятов.
- 97 повторяющихся строк transactions НЕ удалять автоматически: transaction_id отсутствует, исходные строки сходятся с edges.
- Проверять не только совпадение пар edges/transactions, но и суммы и n_tx. В starter суммы/количества агрегируются, но не проверяются assert-ами.
- Деньги сравнивать с явной точностью; для сумм предпочтительны целые тиыны после контролируемого округления.
- Обрыв depth=4 запрещает вывод «terminal» только из нулевого outflow. Входящие признаки консолидации на границе использовать можно.
- Неполный inflow касается всех узлов, особенно seed. `out/in` не является бухгалтерским балансом или долей именно тех же денег.
- `out/in > 1` не является самостоятельной аномалией. Нулевой знаменатель → отсутствующий показатель, а не infinity.
- Только июль 2026, внутрибанковские переводы ≥5000 KZT. Меньшие суммы, другие банки, остатки и другие периоды не наблюдаются.
- Даты имеют точность до дня. Внутридневной порядок операций неизвестен.
- Путь в агрегированном графе не доказывает хронологическую цепочку или происхождение средств.
- Нельзя придумывать ФИО, ИИН, организацию, тип бизнеса, доход, обналичивание или виновность.

## Аналитика и объяснимость

- Разделять role, heuristic role_score, investigation priority и ограничения наблюдаемости.
- Score не является вероятностью преступления или статистически откалиброванной вероятностью роли.
- Каждый критерий имеет версию, признаки и пороги; см. стартовую спецификацию в BUILD_BRIEF.
- При пересечении ролей хранить secondary signals; основной role выбирать по документированному правилу.
- Если данных недостаточно: `peripheral` как fallback с `insufficient_evidence` и низким role_score. Это не утверждение о безопасности клиента.
- Не принуждать распределение к наличию всех шести ролей и не назначать coordinator только по центральности.
- Для betweenness использовать направленный невзвешенный граф в MVP. `sum_kzt` как расстояние не использовать.
- Для Louvain неориентированная проекция суммирует A→B и B→A; исходный направленный граф сохраняется для потоков.
- Фиксировать random seed, версии библиотек, порядок входных узлов и стабильную нумерацию кластеров. Не подгонять количество кластеров к восьми.
- Гипотеза кластера строится шаблоном из рассчитанных признаков и помечается как гипотеза.
- Полное evidence хранить структурированно; CSV evidence — краткое представление тех же фактов.

## AI

- Максимум один Investigator; без отдельного LLM Verifier в MVP.
- Только read-only инструменты с ограничением числа результатов, hops и времени исполнения.
- Нет shell, произвольного Python/SQL, web enrichment, изменения score или блокировки счетов.
- Ответ: findings, evidence_ids, gids, limitations, next_checks.
- Backend проверяет существование gid/evidence, соответствие фактов snapshot и обязательные ограничения. Свободный текст не считается полностью доказанным только потому, что JSON прошёл schema validation.
- Числовые утверждения желательно отображать из fact objects/template на стороне приложения, а не переписывать моделью.
- При ошибке/таймауте AI граф, карточки, поиск, CSV и приоритеты продолжают работать.
- Operational trace показывает реальные вызовы и результаты, не скрытую цепочку рассуждений.
- Не добавлять декоративный HumanGate: в MVP нет действий с финансовыми последствиями.

## Команда и порядок работы

- Нурасыл: product/scope, правила аналитики и evidence, затем Investigator и demo narrative.
- Даулет: `backend/` и `pipeline/`, реализация расчётов, CSV, API, интеграция и запуск.
- Аки: `frontend/`, один основной экран, граф, карточка, затем материалы демо.
- Нурасыл утверждает смысл общего контракта; Даулет поддерживает его runtime-реализацию. Аки работает с согласованным JSON fixture.
- Не переименовывать поля и не менять чужие директории без необходимости и синхронизации. Не отменять чужие незакоммиченные изменения.
- Сначала работающий путь Parquet → CSV → список → карточка/граф. Агент подключается к готовым данным.
- Если обязательное ядро не готово — заморозить AI и polish.
- Последние 90 минут — freeze, воспроизводимость, README, репетиция и сдача. При меньшем остатке времени сокращать scope, а не проверки обязательных результатов.

В отчёте о работе писать: что сделано, чем проверено, что пока не работает. Не объявлять scaffold, mock или исследовательский аудит готовым продуктом.

## Инструкция frontend-агенту

**Цель:** пользователь за первые 10 секунд понимает, что за сеть открыта, кого смотреть первым и почему. Центральный workflow — список → выбранный узел → связи и evidence.

Порядок:

1. Получить утверждённый fixture: summary, entity, subgraph, cluster и error.
2. Создать один экран и явные loading/error/empty states.
3. Показать top-list, поиск полного gid, выбранный dossier и направленный граф.
4. Подключить реальный backend без переименования полей.
5. Добавить фильтры, выбор узла, отображение ограничений и скрытых соседей.
6. Только затем подключить необязательную Investigator-панель и polish.

Acceptance:

- ID в React и graph library всегда string. Если библиотека требует внутренний numeric index, хранить отдельное точное соответствие, никогда не конвертировать исходный gid в Number.
- Метрики приходят от backend. Нельзя вычислять degree, суммы, роли или scores по урезанному видимому подграфу.
- На графе есть стрелки, легенда и явный выбранный узел. Изолят имеет полноценную карточку и сообщение об отсутствии наблюдаемых связей.
- UI различает «данные ещё загружаются», «узел не найден», «нет связей», «AI недоступен» и «выборка ограничена».
- Искать нужно по полному dataset, а не только по top-20. Урезанный граф показывает omitted_count и возможность просмотреть остальных соседей.
- Приоритет и уверенность подписаны раздельно. Не писать «вероятность отмывания 87%».
- Не строить routing на много страниц, custom graph engine или сложный state management без необходимости.

## Инструкция backend/pipeline-агенту

**Цель:** воспроизводимо получить все обязательные результаты и дать UI/AI одну согласованную модель данных.

Порядок:

1. Реализовать загрузку с понятными ошибками схем/путей и проверкой согласованности.
2. Построить полный граф, включая изоляты; рассчитать базовые признаки и flags.
3. Реализовать предложенные правила из BUILD_BRIEF в конфигурации/функциях, не в prompt.
4. Получить кластеры, роли, приоритеты и evidence; проверить CSV schemas и invariants.
5. Сохранить общий snapshot; API и agent tools должны читать его, а не независимо повторять бизнес-логику.
6. Подключить routes, обработать неизвестный gid, пустое окружение и AI outage.
7. Документировать реальные команды и измеренный runtime. Проверить запуск без ключей.

Acceptance:

- Три Parquet явно задаются через директорию входных данных; никаких абсолютных путей с компьютера автора.
- Все 2248 строк сохраняются. У изолятов и boundary есть корректные cluster, role fallback и limitations.
- Сумма n_tx и sum_kzt сверяется с transactions; одинаковые transactions не удаляются молча.
- Нулевой знаменатель не превращается в infinity; JSON строго валиден.
- CSV и API используют один расчёт score. Сортировки, rounding и tie-breaking определены явно.
- Ошибка входной схемы останавливает расчёт с объяснением; частично записанные файлы не выдаются за successful run.
- Для CSV следует учитывать escaping запятых/переносов через штатный writer; evidence длина проверяется после генерации.
- Export принимает только разрешённые имена файлов и не читает произвольные пути.
- Обязательное ядро не импортирует пакет агента при старте CLI. LLM-key не является условием запуска API для чтения готовой аналитики.

## Инструкция agent-агенту

**Цель:** дать один полезный путь уточняющего исследования с проверяемыми ссылками, без замены аналитики генерацией текста.

До готового snapshot заниматься методологией, контрактом tool results и ограничениями. Можно проверить тонкий model-call harness отдельно, но не объявлять это выполнением кейса и не отвлекать backend от CSV.

Порядок:

1. Согласовать профиль/evidence и определить 3–4 инструментальных операции.
2. Реализовать read-only adapters к тем же Python-функциям/snapshot, что использует API.
3. Настроить один agent loop с bounded execution и structured output.
4. Добавить программную проверку ссылок/чисел и обязательных limitations.
5. Проверить реальный вопрос, несуществующий gid, отсутствие общих получателей и таймаут.
6. Подключить результат к UI; сделать реальные tool calls видимыми в activity.

Acceptance:

- Инструмент `find_common_recipients` различает прямые переводы и структурную достижимость. Список путей имеет ограничение длины/количества и не заявляет хронологическую передачу средств.
- Модель не получает весь dataset как огромный prompt, а запрашивает ограниченные результаты.
- GID во всех tool schemas — string, списки gid — array of strings.
- Результат не содержит новых ролей, самостоятельно рассчитанных score или несуществующих evidence IDs.
- При непроверяемом выводе ответ ограничивается имеющимися facts и указывает нехватку данных; повторный LLM не используется как доказательство.
- Model timeout возвращает понятный статус, не уничтожает snapshot и не мешает остальному интерфейсу.
- Не давать агенту инструменты банковских действий, внешнего поиска, shell, файлового редактирования или произвольного выполнения кода.
- Не подключать specialist, отдельный verifier, memory storage или planner без нового решения о scope.

## Интеграционный контракт и fixtures

Минимальные сущности:

- `Entity`: точный gid, depth/is_seed, role, role_score, priority_score, cluster_id, metrics, evidence, limitations, next_checks.
- `Edge`: строковые src/dst, наблюдаемые sum_kzt и n_tx; направление всегда src→dst.
- `Subgraph`: nodes, edges, признак ограничения и количество скрытых результатов.
- `Cluster`: cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids и hypothesis.
- `InvestigationResult`: findings с evidence_ids/gids, limitations, next_checks, фактически выполненные tool calls и статус.

Это семантический список, а не разрешение каждому слою придумать свою сериализацию. Схемы реализует backend; конкретные route shapes фиксируются в BUILD_BRIEF и shared fixtures до интеграции.

Для одного и того же поля не использовать одновременно `score`, `risk`, `priority` и `priority_score`. Не переименовывать `gid` в `customerId` на одном слое. UI-адаптеры допустимы только явно, без потери точности и изменения смысла.

Fixtures нужны для разработки UI, но финальный demo и CSV используют исходные данные. Все mocks маркируются как mocks. Fallback — отображение последнего проверенного результата, а не выдуманный success response.

## Правила реализации аналитики v0

Точные условия и формулы — только в BUILD_BRIEF/config; не создавать вторую независимую версию внутри агента или React.

- Условие допуска роли применяется до сравнения score. Нельзя получить terminal на depth=4 за счёт большого score.
- Percentile normalization должна явно определять референсную группу, обработку нулей и ties; не использовать высокий percentile из группы в два узла как сильное доказательство.
- Coordinator требует сочетания сигналов; одиночный maximum PageRank/betweenness недостаточен.
- Role uncertainty не обнуляет автоматически investigation priority. В карточке можно показать важный узел с ограниченной уверенностью в роли.
- Temporal signal обозначает согласованность дат наблюдаемых операций. В пределах одного дня порядок неизвестен; окно конца месяца создаёт дополнительную цензуру.
- Community labels стабильны только для конкретного snapshot/config. Не обещать неизменные cluster_id при изменении данных.
- При формировании evidence сохранять точные исходные значения; округлять только отображение. Число в короткой карточке должно согласовываться с полным профилем.
- Любое изменение методологии сопровождается повторным расчётом всей выборки и проверкой нескольких разных профилей, не только удачного demo node.
