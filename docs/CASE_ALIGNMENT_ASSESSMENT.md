# Оценка соответствия официальному кейсу

**Срез кода:** ветка `codex/frontend`, исходный commit `91cb23a` (до добавления этого отчёта), 23 сентября 2026 года.

**Основание:** официальное ТЗ и данные в `case/`, код текущей ветки, тесты и зафиксированные результаты запусков в README. В рамках этой оценки тесты и сборка повторно не запускались; выводы об их прохождении ниже относятся к записанным результатам.

## Короткий вывод

**Основной сценарий кейса реализован в значительной степени: все пять must-have представлены в коде, а ключевые свойства аналитики проверяются тестами. До статуса полностью готовой сдачи ещё есть пробелы в воспроизводимости на чистом устройстве и в демонстрационных материалах.**

Моя ориентировочная оценка готовности репозитория — **около 80/100** (разумный диапазон — **75–83**), а не прогноз оценки жюри. Это оценка соответствия и подтверждённости результата, не точности выявления ролей: в кейсе нет размеченных ролей, поэтому измерить accuracy по имеющимся данным нельзя.

Важно ограничить обещание продукта: инструмент формирует приоритеты и гипотезы по **наблюдаемой** сети. Он не восстанавливает доказанную преступную организацию, не устанавливает виновность и не подтверждает происхождение средств.

## Что сделано особенно хорошо относительно ограничений данных

- Граф строится со всеми узлами, в том числе 19 изолированными seed; проверки охватывают также depth=4 и узлы с выходом больше наблюдаемого входа.
- Суммы и количества транзакций сверяются с `edges`; повторяющиеся строки не выбрасываются автоматически.
- `gid` сохраняется точным: Python/Parquet используют целочисленные значения, API и React — строки. Тест проверяет идентификаторы за пределами точности JavaScript.
- Ролевой score и priority разделены; priority объясняется шестью числовыми вкладами. Ни один из этих баллов не выдаётся за вероятность преступления.
- Оговорки о неполном входящем потоке, обрыве глубины, датах без времени и недоказанном происхождении средств присутствуют в коде/контракте и интерфейсе.
- Нет жёстко заданных результатов по конкретным gid и внешнего обогащения клиентских данных.

Это существенно повышает методологическое соответствие: интерфейс не только показывает кандидатов, но и обозначает, какие выводы из доступных данных делать нельзя.

## Пробелы до завершённого submission

1. **Нет подтверждённого cold start на другом компьютере или macOS.** В `README.md`/`integration/README.md` эта проверка прямо отмечена незакрытой. Текущий успешный runtime относится к Windows.
2. **Экспортируемые CSV не входят в Git.** Локальные `pipeline/out/*.csv` и `snapshot.json` игнорируются правилом `pipeline/.gitignore`. Это нормально для генерируемых файлов, но перед сдачей нужно убедиться, что жюри запускает pipeline и получает CSV, либо приложить итоговые выгрузки отдельным способом.
3. **Нет обнаруженного отдельного слайда/файла со схемой решения и подтверждения пяти минут репетиции.** Архитектура и сценарий описаны текстом в README и `docs/BUILD_BRIEF.md`; этого достаточно для понимания, но не подтверждает готовность требуемого демонстрационного артефакта.
4. **Статусные документы расходятся.** Корневой README описывает работающие pipeline/API/UI, тогда как начало `docs/BUILD_BRIEF.md` всё ещё говорит «продукт пока не реализован», а `agent/README.md` — что live service и HTTP route не подключены. Это исторические формулировки, противоречащие текущему backend/integration-коду, и они могут запутать проверяющего.
5. **Последний frontend-коммит менял отображение результатов Investigator.** В доступной записи интеграционного прогона есть успешная сборка более раннего состояния; данный аудит не запускал `npm run build` повторно после `91cb23a`.

## Investigator и другие необязательные функции

Официальное ТЗ называет AI-ассистента опциональным. Read-only tools уже работают поверх того же live snapshot, API/UI честно обрабатывают состояние без модели, но реальный model adapter не подключён: `/api/investigate` сейчас возвращает `unavailable`. Поэтому это **не блокирует пять must-have**, но нельзя заявлять, что пользователь уже может получить живой ответ от AI. Временные паттерны, циклы, детекция аномалий и симуляция устойчивости тоже не реализованы; кейс относит их к опциям.

## Самые полезные следующие шаги

1. Обновить противоречивые статусные абзацы, чтобы во всех точках входа было ясно: live core работает, модель Investigator отсутствует.
2. Выполнить полный запуск по README в чистом окружении и записать ОС, версии, команду, время и фактическое наличие трёх CSV.
3. После последнего изменения интерфейса повторить production build и ручной сценарий: произвольный gid, изолят, узел depth=4, направленные связи и экспорт.
4. Собрать один читаемый артефакт со схемой данных → аналитики → API/UI и подготовить тайминг 5-минутного демо с 2–3 разными узлами.
5. Перед передачей проверить наличие CSV в пакете сдачи, поскольку Git их сейчас игнорирует.

Подключать живую модель имеет смысл только если остаётся время после этих пунктов: для соответствия обязательному ядру она не нужна.
