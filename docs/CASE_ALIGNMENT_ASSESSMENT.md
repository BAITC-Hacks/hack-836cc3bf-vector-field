# Оценка соответствия официальному кейсу

**Срез кода:** `origin/codex/frontend` на `ea0693d`, включая live Investigator из Stage 2 (`origin/main` на `e531df0`), 23 сентября 2026 года.

**Основание:** официальное ТЗ и данные в `case/`, код текущей ветки, тесты и зафиксированные результаты запусков в README и `integration/STAGE2_CLOSURE.md`. В рамках этой оценки тесты и сборка повторно не запускались; выводы об их прохождении ниже относятся к записанным результатам.

## Короткий вывод

**Решение близко к полному по функциональному ядру: все пять must-have реализованы, pipeline измеренно работает за секунды, а два сценария Investigator проверены с настоящей OpenAI-моделью. До полностью закрытой сдачи остаются межмашинная проверка, демонстрационный пакет и повторная проверка completed-AI сценария после последнего UX-полиша.**

Моя ориентировочная оценка готовности репозитория — **около 85/100** (разумный диапазон — **81–87**), а не прогноз оценки жюри. Это оценка соответствия и подтверждённости результата, не точности выявления ролей: в кейсе нет размеченных ролей, поэтому измерить accuracy по имеющимся данным нельзя.

Важно ограничить обещание продукта: инструмент формирует приоритеты и гипотезы по **наблюдаемой** сети. Он не восстанавливает доказанную преступную организацию, не устанавливает виновность и не подтверждает происхождение средств.

## Что сделано особенно хорошо относительно ограничений данных

- Граф строится со всеми узлами, в том числе 19 изолированными seed; проверки охватывают также depth=4 и узлы с выходом больше наблюдаемого входа.
- Суммы и количества транзакций сверяются с `edges`; повторяющиеся строки не выбрасываются автоматически.
- `gid` сохраняется точным: Python/Parquet используют целочисленные значения, API и React — строки. Тест проверяет идентификаторы за пределами точности JavaScript.
- Ролевой score и priority разделены; priority объясняется шестью числовыми вкладами. Ни один из этих баллов не выдаётся за вероятность преступления.
- Оговорки о неполном входящем потоке, обрыве глубины, датах без времени и недоказанном происхождении средств присутствуют в коде/контракте и интерфейсе.
- Нет жёстко заданных результатов по конкретным gid и внешнего обогащения клиентских данных.

Это существенно повышает методологическое соответствие: интерфейс не только показывает кандидатов, но и обозначает, какие выводы из доступных данных делать нельзя.

## Пробелы до завершённого submission

1. **Нет подтверждённого cold start на другом компьютере или macOS.** В `README.md`/`integration/README.md` эта проверка прямо отмечена незакрытой. Текущий успешный runtime относится к Windows.
2. **Экспортируемые CSV не входят в Git.** Локальные `pipeline/out/*.csv` и `snapshot.json` игнорируются правилом `pipeline/.gitignore`. Это нормально для генерируемых файлов, но перед сдачей нужно убедиться, что жюри запускает pipeline и получает CSV, либо приложить итоговые выгрузки отдельным способом.
3. **Схема решения и демо описаны, но отдельного слайда и подтверждения 5-минутной репетиции не найдено.** README содержит поток Parquet → аналитика → CSV/snapshot → API/UI, а `frontend/FINAL_UX_GATE.md` — рекомендуемый сценарий. Это хорошая основа, но не доказательство готового презентационного артефакта или тайминга.
4. **Осталась одна заметная статусная нестыковка.** Корневой README, `agent/README.md` и интеграционные отчёты описывают рабочий live Investigator, тогда как вводная строка `docs/BUILD_BRIEF.md` всё ещё говорит «продукт пока не реализован». Проверяющему стоит читать BUILD_BRIEF как историческое описание scope, а статус брать из README и integration closure.
5. **Completed Investigator не перепроверен после финального UI-полиша.** `integration/STAGE2_CLOSURE.md` фиксирует два настоящих OpenAI browser-сценария; `frontend/FINAL_UX_GATE.md` фиксирует более позднюю сборку и ручную проверку UI, но completed AI и переход из finding в граф в этом последнем UX gate отмечены `NOT RUN`.

## Investigator и другие необязательные функции

Официальное ТЗ называет AI-ассистента опциональным. В актуальном коде OpenAI Responses adapter подключён к `/api/investigate`; без `OPENAI_API_KEY` endpoint честно возвращает `unavailable`, а с ключом использует четыре read-only tools поверх общего snapshot. `integration/STAGE2_CLOSURE.md` фиксирует реальные browser smoke для ranking и node profile, с проверкой фактов и tool trace. Это сильное усиление технической части, но не обязательное условие must-have. Свободный текст модели всё ещё не может быть полностью семантически доказан; документированные проверки ограничены двумя сценариями. Временные паттерны, циклы, детекция аномалий и симуляция устойчивости не реализованы; кейс относит их к опциям.

## Самые полезные следующие шаги

1. Обновить вводный статус `docs/BUILD_BRIEF.md`, чтобы он не противоречил README и Stage 2 closure.
2. Выполнить полный запуск на чистом клоне/втором устройстве и записать ОС, версии, время и полученные CSV; macOS/Linux пока отдельно не подтверждены.
3. Провести один completed Investigator smoke на последнем frontend UI и проверить переход из finding к точному gid/графу.
4. Добавить экранный путь для кластеров или решить, что достаточно CSV/API для сценария жюри; сейчас кластер виден в сводном количестве и карточке, но не как отдельная группа на графе.
5. Подготовить отдельную схему решения и прогнать демо с таймером до пяти минут на 2–3 разных узлах.
6. Перед передачей проверить, что три CSV доступны жюри: Git игнорирует локальную папку `pipeline/out/`, хотя команда pipeline воспроизводимо их создаёт.

Новый функционал сейчас менее важен, чем проверка сдачного сценария: AI-адаптер уже подключён и имеет два live smoke, а пять обязательных требований кейса от этого не зависят.
