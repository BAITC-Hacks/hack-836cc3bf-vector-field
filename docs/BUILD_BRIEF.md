# HackAlem — что строим сейчас

Статус: согласованное направление после проверки кейса и данных. Это план реализации; продукт пока не реализован. Исторический Full Team Execution Plan использовать только для ритма, интеграции и freeze, не для agent-first порядка работ.

## Продукт и результат

**Инструмент, который из выгрузки финансовой сети формирует объяснимую очередь проверки клиентов и позволяет проверить каждый вывод на графе.**

Пользователь — AML-аналитик банка. Он уже имеет 81 исходного участника и выгрузку связей. Его задача — найти важные точки консолидации и другие значимые узлы среди 2248 клиентов.

Core outcome: минимум 20 ранжированных клиентов, роли всех узлов, кластеры и числовые основания выводов. Результат можно открыть, проверить и экспортировать.

Не обещаем восстановить всю реальную преступную организацию. Анализируем наблюдаемую сеть и формируем гипотезы для проверки.

**Demo story:** аналитик открывает выгрузку → получает приоритеты → выбирает узел → видит роль, связи и evidence → проверяет ограничение данных → экспортирует результат; затем может задать уточнение Investigator.

## Аналитический pipeline

1. Прочитать nodes, edges, transactions. Проверить схемы, null, уникальность gid/пар, endpoints и агрегаты сумм/количеств.
2. Добавить все nodes в DiGraph, затем направленные edges с `sum_kzt,n_tx`.
3. Посчитать in/out degree, суммы, количества транзакций, direct seed senders, directed seed reach ≤4 hops и флаги наблюдаемости.
4. Определить weak components; выполнить Louvain на явно описанной неориентированной проекции внутри компонент. Изоляты — отдельные кластеры.
5. Посчитать направленную unweighted betweenness. PageRank оставить диагностическим, не главным критерием роли или приоритета.
6. Вычислить role signals, основной role, role_score, priority и структурированное evidence.
7. Сформировать cluster summaries/hypotheses, top list, CSV и snapshot для UI/AI.
8. Проверить output contracts, сохранить config/rules version и время выполнения.

`analysis/audit_dataset.py` уже проверяет данные и считает исследовательские метрики. Он **не заменяет** пункты 6–8 и не выдаёт готовых ролей. Starter можно использовать как основу, исправив неполные проверки и добавление изолятов.

## Стартовая спецификация ролей

Это **предложенная эвристика v0**, а не обученная модель или подтверждённая точность. Нурасыл должен принять/скорректировать пороги перед реализацией; не подбирать их по списку «нужных» gid.

Обозначения: `I/O` — наблюдаемые вход/выход в KZT, `di/do` — разные отправители/получатели, `ti/to` — количества транзакций, `r=O/I` при I>0. `p(x)` — нормализация ненулевого признака к [0,1] по эмпирическому percentile среди допустимых узлов; x=0 даёт 0, ties обрабатываются одинаково. Для очень маленькой группы использовать общую референсную группу, не её локальный top-1.

| Роль | Условие допуска | Сила сигнала s в [0,1] | Обязательная оговорка |
|---|---|---|---|
| consolidator | di≥3 | 0.7·p(di)+0.3·p(ti) | Это схождение переводов, не доказательство накопления остатка |
| distributor | do≥10 | 0.7·p(do)+0.3·p(to) | Получатели неизвестного назначения; не выводить тип деятельности |
| transit | I>0, O>0, ti≥2, to≥2, 0.8≤r≤1.2, не seed, depth<4 | 0.6·max(0,1−abs(r−1)/0.2)+0.4·p(min(ti,to)) | Сходство объёмов; без дат нельзя утверждать сквозное движение тех же денег |
| terminal | Не seed, depth<4, I>0, r≤0.1, вход на ≥2 датах; последний вход не позже 29 июля | 0.6·(1−min(r/0.1,1))+0.4·p(ti) | Только кандидат в наблюдаемый конечный получатель; нет остатков и внешних переводов |
| coordinator | di>0, do>0, достижим от ≥2 seed; betweenness ≥90-го percentile положительных значений; ≥20% наблюдаемого incident volume пересекает кластеры | 0.6·p(betweenness)+0.4·p(seed_reach_4) | Структурный посредник; управление людьми или организацией не установлено |
| peripheral | Ни одно правило не прошло | fallback | Нет достаточных признаков заданных ролей; это не низкий AML-риск |

Роль transit без temporal-подтверждения остаётся слабой гипотезой. Координатор зависит от кластеризации и структуры выборки; не пытаться обязательно найти его любой ценой.

**Выбор основной роли:** для допустимых ролей посчитать `role_score=s*q`, выбрать максимум; при равенстве фиксированный порядок `consolidator,distributor,transit,terminal,coordinator`. Сохранять остальные допустимые роли как secondary signals.

Стартовые q: consolidator/distributor 0.85; transit 0.60; terminal 0.50; coordinator 0.55. Это консервативные policy-множители для MVP, **не измеренная вероятность**. Указывать это в README. При единичной транзакционной поддержке cap=0.40; для fallback peripheral score=0.15, для изолята=0.05. На depth=4 terminal запрещён; если есть fan-in, consolidator разрешён, иначе fallback с явным `depth_truncated`.

Не считать низкий role_score доказательством низкой важности. При близких двух score (разница <0.10) показать «смешанные признаки» и обе роли в карточке. Роль в обязательном CSV остаётся одна.

Проверить итоговое распределение и 3–5 случайных узлов; если правило создаёт бессмысленную массовую разметку, изменить правило для всех узлов и зафиксировать версию. Наличие ground truth не заявлять.

## Investigation Priority v0

Приоритет выражает полезность проверки в данном расследовании. Он не обязан совпадать с role_score.

Простая стартовая формула:

```text
S = 0.5*p(direct_seed_senders) + 0.5*p(seed_reach_4)
C = p(in_degree)
V = p(max(in_kzt, out_kzt))
B = p(directed_unweighted_betweenness)
D = p(out_degree)
priority_score = 0.35*S + 0.25*C + 0.20*V + 0.10*B + 0.10*D
```

Изолят получает 0 по наблюдаемой сети и отдельный data-gap статус. Его принадлежность к seed не исчезает. Нельзя объяснять этот 0 отсутствием подозрений.

Это прозрачный baseline для старта, а не оптимальные веса. Полезные проверки до freeze: сравнить top-20 с простым ранжированием по сумме/degree; изменить веса на ±20% с перенормировкой и посмотреть пересечение top-20; проверить, не вытеснены ли все небольшие компоненты. Не рисовать accuracy без разметки.

Evidence для priority показывает 2–3 крупнейших вклада. Не перемножать весь priority на confidence: важный узел с неполными данными может требовать срочного запроса информации. Отдельно показать «приоритет высокий; уверенность в конкретной роли ограничена».

Сумма потоков через несколько рёбер может повторно учитывать одни и те же деньги. 365.89 млн KZT — сумма наблюдаемых переводов, не объём уникальных преступных средств.

## Кластеры

Louvain подходит для MVP. Использовать `weight(A,B)=sum(A→B)+sum(B→A)`, seed=42, resolution=1 и фиксированные версии. Отдельные weak components не смешивать. Идентификаторы назначать после сортировки кластеров по размеру и минимальному gid.

`sum_kzt_internal` — сумма исходных направленных рёбер, оба конца которых в кластере, каждое ровно один раз. `top_gids` — до 3 узлов по тому же priority; формат CSV — список десятичных gid через `;`. `hypothesis` — шаблон по доминирующим признакам, seed и потокам; никаких «наркогрупп» или «обнальных компаний».

В аудите три запуска дали 103–105 кластеров, в каждом 8 кластеров с несколькими seed. Это НЕ означает, что «правильный ответ — 8 кластеров», и не доказывает стабильность состава этих восьми групп.

## Evidence и data gaps

Единый fact object для Python → CSV/UI/AI:

```json
{
  "evidence_id": "node:<gid>:fanin:v1",
  "gid": "<exact decimal gid>",
  "metric": "in_degree",
  "value": 13,
  "rule_id": "consolidator_v0",
  "source": "edges.parquet",
  "scope": "observed_intrabank_july_2026",
  "limitations": ["inflow_incomplete"]
}
```

Полное evidence должно позволять открыть соответствующие рёбра и транзакции. У исходных транзакций нет tx_id; локальный row reference привязывать к hash исходного файла и номеру строки, не выдавать за банковский ID.

CSV-пример для реально наблюдаемого профиля: «13 плательщиков; вход 1 095 690 KZT; 1 получатель, выход 66 000 KZT. Признаки консолидации; вход неполон». CSV-текст генерируется шаблоном и валидируется по длине.

| Ограничение | Следующий запрос данных |
|---|---|
| depth=4 | Исходящие переводы следующего колена за тот же период |
| Неполный inflow / out>in | Полная входящая история узла за июль, включая внешние по отношению к графу источники |
| Кандидат terminal | Остатки, межбанковские/прочие исходящие и операции после конца окна |
| Подозрение на быстрый transit | Точное время входящих/исходящих; дневной порядок неизвестен |
| Изолированный seed | Причина отсутствия операций: порог, период, канал или действительно нет наблюдаемых переводов |

Не назначать автоматически «±30 дней» без причины. Сначала запросить именно отсутствующую сторону наблюдения; расширение периода — отдельная обоснованная рекомендация.

## Минимальный API contract

Предлагаемые endpoints; согласовать один раз, затем не менять независимо в разных слоях:

| Endpoint | Результат |
|---|---|
| `GET /api/summary` | Размеры, ограничения, компоненты, top nodes, версия расчёта |
| `GET /api/entities/{gid}` | Роль, scores, метрики, evidence, flags, next checks |
| `GET /api/subgraph?gid=...&hops=1&limit=80` | Узлы/рёбра окружения, counts, `truncated`, `omitted_count` |
| `GET /api/clusters` | Сводки кластеров |
| `GET /api/export/{filename}` | Один из трёх разрешённых CSV, без произвольного пути |
| `POST /api/investigate` | Опциональный AI-вопрос с selected_gids; grounded ответ |

Результат для узла: `gid:string, role:string, role_score:number, cluster_id:integer, priority_score:number, metrics:object, evidence:array, limitations:array, next_checks:array`.

Все API и tools читают один snapshot. Даты — ISO. Неизвестный gid — понятный 404, отсутствие соседей — успешная пустая выборка. `NaN/Infinity` в JSON запрещены. UI не пересчитывает метрики по показанному подграфу: он часто урезан.

## Один Investigator

Core без AI полностью работоспособен. AI полезен для перевода вопроса аналитика в последовательность операций над рассчитанной сетью.

Четыре инструмента достаточно:

1. `get_entity_profile(gid)` — признаки, роли, evidence, ограничения.
2. `get_subgraph(gid,hops,limit)` — направленное окружение.
3. `find_common_recipients(gids,max_hops,limit)` — общие получатели с путями-свидетельствами и явным указанием direct/reachable.
4. `rank_entities(role,cluster_id,limit)` — готовое ранжирование с фильтром.

Пример: «Кто собирает переводы от выбранных seed?» → общие получатели → профили кандидатов → список с причинами и оговорками → клик выделяет подтверждающие связи.

Начальный лимит: до 6 tool calls на вопрос, hops≤4, ограниченный output и общий timeout; подобрать timeout по измеренной API latency. Без отдельного specialist/verifier, без бесконечных retries. Проверять evidence_ids/gids и выводить числовые facts из snapshot. Наличие ссылок само по себе не доказывает любой свободный вывод модели.

Не давать AI назначать роли, менять приоритет, придумывать суммы, утверждать, что одни и те же деньги прошли путь, определять виновность или выполнять банковские действия.

## UX: четыре поверхности в одном экране

1. **Brief:** 2248 узлов, 81 seed, период, 35 компонент (16 с рёбрами), предупреждение о границах данных.
2. **Priority list:** ≥20 узлов, роль, priority, краткая причина; глобальная сортировка, фильтры «новые/seed», cluster/role.
3. **Graph:** ego-граф выбранного узла, стрелки, поиск, переключение кластеров; полный обзор по запросу.
4. **Dossier + Investigator drawer:** метрики, роль/secondary signals, evidence, ограничения, следующий запрос; AI-вопрос контекстен выбранным узлам.

Первые 10 секунд должны отвечать «что за выборка», «кого смотреть первым» и «почему». Клик на high-priority node синхронно открывает карточку и связи.

Цвет — роль; seed — отдельная обводка; selected — выделение; boundary — явный значок. Размер ограничен диапазоном, чтобы один hub не съел экран. Cluster показывать фильтром/группировкой, не вторым конфликтующим кодированием цвета. GID сокращать только визуально, полный ID копируется и ищется точно.

Предел 80 узлов — стартовый UI cap, а не свойство сети. Для узла со 116 получателями показывать количество скрытых соседей и кнопку раскрытия/списка. При фильтрации явно показывать, что связи скрыты.

## Масштабирование: только текст в README

При ~1 млн узлов pandas/NetworkX и точная all-pairs betweenness могут стать узким местом. Перейти к columnar/partitioned preprocessing, компактному графовому backend, приближённой или локальной центральности, пакетному community detection и серверным подграфам. UI получает только нужное окружение. Историю/snapshots хранить отдельно от процесса. Выбор хранилища зависит от реальных запросов; Neo4j не является автоматическим требованием. Не реализовывать это на хакатоне.

## Definition of Done

Все три CSV валидны; каждый исходный gid присутствует; для 3 произвольных узлов можно за минуту объяснить правило; AI outage не ломает core; пересчёт <5 минут; поиск и направления связей работают; README соответствует командам; правила и ограничения доступны; есть схема и проведённая репетиция.

Финальное позиционирование: **«От известных участников — к объяснимой очереди проверки финансовой сети».**
