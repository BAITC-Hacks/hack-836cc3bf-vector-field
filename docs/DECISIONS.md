# Зафиксированные решения после внешнего review

Дата: 23 сентября 2026. Цель — снять неоднозначности до параллельной реализации. Этот документ уточняет BUILD_BRIEF/API_CONTRACT, не расширяет scope. Отсчёт 270 минут из EXECUTION_PLAN не запускается заново при чтении этого файла.

## D-01 — Концепция заморожена

Сохраняем deterministic pipeline → CSV/snapshot → API → очередь/карточка/граф. Один Investigator после Core Green. Frontend и backend работают параллельно через fixtures; схема зависимостей не означает, что Аки ждёт готового pipeline. Нурасыл может параллельно готовить tool adapters и prompts на fixtures, но не отнимать время у правил и проверки аналитики.

Новых экранов, метрик «информативности», enrichment, второго агента и БД не добавляем. Review не является поводом ещё раз проектировать продукт.

## D-02 — Priority должен объясняться в карточке

Принимаем замечание. Формула из BUILD_BRIEF сохраняется, веса не переизобретаются. Их смысл — выбранная политика приоритизации для MVP, а не выученная оптимальная модель.

На вопрос «почему 0.82?» показываем сумму рассчитанных вкладов, исходные признаки и формулу нормализации. На вопрос «почему такие веса?» отвечаем: это прозрачная эвристика, отдающая больший вес связи с seed и fan-in; оптимальность не установлена, проверяем чувствительность ранжирования. Разложение делает расчёт проверяемым, но само по себе не доказывает качество приоритетов.

Backend сохраняет шесть вкладов в existing evidence, frontend показывает крупнейшие и «прочие», агент использует те же facts. Сумма вкладов должна совпадать с priority_score с числовым допуском 1e-9 до display rounding. Role score отдельно, priority никогда не копируется из role_score.

Не добавляем «потенциальную информативность проверки» в формулу: пока нет формального измеримого определения. Неполнота данных отражается в limitations и next check, а не произвольным бонусом каждому неизвестному объекту.

## D-03 — Нормализация и правила больше не оставлены на усмотрение трёх реализаций

Стартовые правила v0 зафиксированы для первого расчёта. Определение positive midrank, quantile coordinator и межкластерной доли уточнено в BUILD_BRIEF. Backend считает один раз по всему snapshot; frontend и агент не пересчитывают. Менять правила можно после обнаружения конкретной ошибки, с версией и полным пересчётом, без исключений по gid.

Support-множители role_score остаются эвристическими. Нельзя подписывать их как измеренную точность или процент уверенности модели. Если нужно уточнить role selection, сначала показать конфликтующие реальные профили, а не оптимизировать число красивых ролей для слайда.

## D-04 — Coordinator: код прежний, подпись осторожная

CSV/API сохраняют обязательный enum `coordinator`. Пользовательская подпись: **«Структурный посредник (кандидат)»**. В пояснении: «Значим для связности наблюдаемой сети; управление участниками не установлено».

Не вводить новый role enum `coordinator_candidate`, не переименовывать поля. Для terminal подпись «Конечный получатель — гипотеза», для peripheral — «Недостаточно признаков роли». Остальные: «Консолидация», «Транзит — гипотеза», «Распределение».

Score можно показывать 0..1 или x100 как «баллы из 100» с понятной подписью. Не ставить знак процента рядом с «вероятностью преступления» или «точностью роли». Цифры в API/CSV остаются 0..1.

## D-05 — Какие тезисы внешнего review НЕ переносим

- **Разные плательщики ≠ независимые участники.** Независимость, общий владелец и организация неизвестны. Пишем «13 различных gid», не «13 независимых источников».
- **Узел не соединяет разные слабосвязные компоненты.** При наличии таких связей это уже одна компонента. Допустимо «связывает сообщества/участки внутри компоненты», если это посчитано.
- **Distributor не обязан отдавать значимую долю полученного.** Вход неполон; основа роли — наблюдаемый fan-out. Ratio не становится обязательным условием.
- **Много отправителей не доказывает концентрацию объёмов.** Fan-in и распределение сумм по отправителям — разные признаки. HHI/концентрацию не заявлять, пока явно не рассчитываем.
- **Возврат к широкому названию workspace не нужен.** Pitch остаётся про очередь проверки и основания; название не должно снова расширять scope.

## Gate перед усилением AI

Открыть произвольный узел и ответить за минуту: какие признаки дали роль, из каких вкладов сложился приоритет, какие ограничения мешают сильному выводу. Если это невозможно без LLM, сначала исправить deterministic evidence.
