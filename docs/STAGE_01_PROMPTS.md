# Этап 1 — три готовых промпта

Первый рабочий блок: ориентир 35–45 минут, а не новый старт 270-минутного таймера. Каждый участник работает в своём клоне/worktree и своей ветке. Перед запуском сохранить текущие изменения, выполнить `git fetch origin` и влить `origin/main` в свою ветку. Не переключать ветки в общем каталоге, используемом другим агентом.

Скопировать один соответствующий блок целиком в coding agent. Промпты поручают реализацию; этот документ сам по себе её не выполняет.

## Даулет — DAULET-01 / pipeline и три CSV

```text
Ты работаешь со мной, Даулетом, backend/integration owner HackAlem.
Моя ветка: codex/backend. Моя зона: pipeline/, backend/.

Сначала проверь git status и текущую ветку. Не отменяй существующую работу.
Если в checkout уже есть реализация, продолжи её, не создавай второй pipeline.
Прочитай AGENTS.md, README.md, официальный кейс и README в case/,
docs/BUILD_BRIEF.md, docs/DECISIONS.md, docs/API_CONTRACT.md,
shared/contracts.ts и docs/EXECUTION_PLAN_270_MIN.md.
Исследовательский analysis/audit_dataset.py и starter можно использовать
как основу понимания загрузки/метрик, но они не являются готовым продуктом.

Цель этапа: один воспроизводимый запуск по реальным Parquet создаёт
nodes_roles.csv, clusters.csv и top_nodes.csv с заполненными результатами.
Не ограничивайся планом или scaffold. Реализуй, запусти, проверь.

Сделай по порядку:
1. В pipeline/ реализуй CLI с --data и --out. Вход по умолчанию можно
   направить на case/data (1)/data относительно репозитория. Обрабатывай
   пробелы в путях и поддерживай Windows/macOS. Зафиксируй зависимости.
2. Проверь схемы, уникальность gid/пар, endpoints, суммы и n_tx
   transactions→edges. Не удаляй повторяющиеся transactions без tx_id.
3. Добавь все nodes, затем edges в направленный граф. Сохрани 19 изолятов.
4. Рассчитай признаки, directed seed reach ≤4, компоненты, Louvain,
   unweighted directed betweenness и data-quality flags по BUILD_BRIEF.
5. Реализуй правила v0 и точную positive-midrank нормализацию из DECISIONS /
   BUILD_BRIEF. Пороги/веса вынеси в версионированную конфигурацию.
   Не проси повторно выбрать архитектуру или формулу. Если найдёшь
   конкретное противоречие, покажи его и минимальный вариант исправления.
6. Посчитай role_score отдельно от priority. Сохрани все шесть вкладов
   priority в структурированном evidence; их сумма равна priority_score.
   Сохрани полные факты в памяти/внутреннем результате для следующего этапа.
7. Сформируй три CSV в точной схеме кейса. Evidence роли ≤200 символов,
   с числами; why объясняет priority. Для каждого cluster нужна гипотеза,
   размер, seed, внутренний оборот и top_gids. Top — минимум 20 узлов.
8. Добавь краткую pipeline/README.md с реально проверенной командой.
   API и snapshot transport подключим следующим этапом: сейчас CSV важнее
   HTTP scaffold. Не трать этот блок на весь FastAPI backend.

Проверь фактическим запуском:
- 2248 уникальных исходных gid, включая изоляты; допустимые роли;
- scores конечные в [0,1], непустой evidence ≤200 символов;
- каждый cluster_id существует, размеры и seed сходятся;
- top отсортирован priority DESC, gid ASC; поля согласованы с nodes_roles;
- depth=4 не получает terminal; out>in не объявляется преступной аномалией;
- повторный расчёт даёт те же аналитические CSV;
- запуск без LLM key, полный runtime <5 минут;
- сумма шести priority-вкладов совпадает с priority_score до округления.

Не делать: AI, БД, внешние API, новые формулы по отдельным gid, frontend,
массовый рефакторинг общей документации. В transport gid должен быть string,
в Python/CSV сохраняй точные исходные целые; не превращай их во float.

Сначала покажи первые работающие CSV. После проверок создай локальный
commit только своих изменений. Не merge в main и не force push.
В конце: команда запуска, пути файлов, время расчёта, результат проверок,
распределение ролей, известные ограничения и следующий шаг для API.
Если этап не закрыт, прямо назови blocker; не выдавай пустые CSV за готовность.
```

## Нурасыл — NURASYL-01 / методология и граница tools

```text
Ты работаешь со мной, Нурасылом, product/architecture/AI owner HackAlem.
Моя ветка: codex/agent. Моя зона: agent/.
Даулет параллельно реализует pipeline и CSV, Аки — frontend на fixtures.
Не дублируй их работу и не меняй pipeline/, backend/, frontend/.

Сначала проверь git status/ветку и существующие изменения.
Прочитай AGENTS.md, README.md, docs/BUILD_BRIEF.md, docs/DECISIONS.md,
docs/API_CONTRACT.md, shared/contracts.ts, shared/fixtures.json,
docs/EXECUTION_PLAN_270_MIN.md и ограничения официального кейса.

Цель этапа: снять смысловые блокеры и подготовить проверяемую read-only
границу Investigator, которую можно подключить к backend без новых схем.
Полный model loop сейчас не является целью. Не начинай новый brainstorm.

Сделай:
1. Проверь зафиксированную v0-методологию на конкретные противоречия:
   depth=4, изоляты, неполный вход non-seed, mixed roles, нормализация,
   разделение role_score/priority. Используй реальные audit metrics.
   Не оптимизируй веса ради красивого top-list. Если критических проблем
   нет, кратко зафиксируй это в agent/STAGE_01_NOTES.md. Если есть —
   опиши максимум 3 конкретных дефекта и минимальные исправления для Даулета.
   Правки общего контракта/правил самостоятельно не публикуй.
2. В agent/ определи тонкий Python Protocol/interface для четырёх tools:
   get_entity_profile, get_subgraph, rank_entities, find_common_recipients.
   Аргументы, limits и результаты строго по docs/API_CONTRACT.md.
   Не создавай собственный формат Entity или другой snapshot schema.
3. Подготовь явно fixture-only provider на shared/fixtures.json для
   локальных проверок формы результата. Для неподдержанного fixture gid
   возвращай честную ошибку, не профиль другого узла. Не рассчитывай
   граф/роли заново и не выдавай fixture responses за live investigation.
4. Подготовь validator structured findings: gid известны текущему snapshot,
   evidence_ids разрешаются в evidence результата, snapshot_id совпадает,
   обязательные ограничения фактов не потеряны. Сравнивай возвращаемые
   facts с trusted tool evidence; провал проверки не должен стать success.
   Явно опиши, что schema/references не доказывают смысл свободного текста.
5. Запиши минимальные инструкции будущего Investigator в agent/:
   один агент, максимум 6 tool calls, read-only tools, gid:string,
   выводы — гипотезы, числа только из facts, ограничения и next checks.
   Никаких обвинений, самостоятельного scoring или банковских действий.
6. Проверь локально valid reference, unknown gid, invalid evidence_id,
   snapshot mismatch и сохранение ограничения depth_truncated.
   Никакой OpenAI API key для этих проверок не нужен.

При отсутствии реального backend оставь явную точку подключения service
provider. Не читай напрямую неизвестный будущий JSON snapshot и не
заставляй Даулета подстраиваться под твой внутренний формат.
Не устанавливай Agents SDK и не строй model loop до необходимости.
Не добавляй verifier, specialist, memory, БД и новую orchestration-систему.

Отдельно перечисли, что нужно получить от Даулета на следующем этапе:
реальный service provider, snapshot_id и profiles с полным evidence.
Подготовка prompts/tools может идти параллельно pipeline; live integration
начинается после готовности данных, а не подменяется fixture demo.

После проверок создай локальный commit только своей области. Не merge main
и не force push. В конце: файлы, выполненные проверки, смысловые blockers,
точка подключения backend и следующий шаг. Не называй готовыми AI-агента
или расследование, если сейчас реализована только граница tools.
```

## Аки — AKI-01 / один экран на contract v1

```text
Ты работаешь со мной, Аки, frontend owner HackAlem.
Моя ветка: codex/frontend. Моя зона: frontend/.
Даулет строит pipeline/API, Нурасыл — методологию и agent tools.

Сначала проверь git status/ветку и уже существующий frontend. Если он есть,
продолжи его; не пересоздавай проект и не меняй стек без необходимости.
Прочитай AGENTS.md, README.md, docs/BUILD_BRIEF.md, docs/DECISIONS.md,
docs/API_CONTRACT.md, shared/contracts.ts и shared/fixtures.json.

Цель этапа: запускаемый React/Vite экран «очередь → выбранный узел →
направленный граф → карточка», пока на общих синтетических fixtures.
Не жди backend. Не ограничивайся макетом или планом: реализуй и запусти.

Сделай:
1. Минимальный frontend; одна страница, без auth и сложного state manager.
   Используй существующий стек. Если проекта нет — React/Vite/TypeScript.
2. Подключи общие types из shared/contracts.ts. Не копируй их с другими
   именами. Сделай data-provider слой, чтобы fixture-provider затем
   заменить HTTP-provider без переписывания компонентов.
3. Слева — priority queue: gid, роль, priority и короткое why.
   В центре — ego-граф выбранного узла со стрелками и выделением.
   Справа — dossier: role_score отдельно от priority, потоки, evidence,
   limitations и next_checks. Не добавляй другие dashboards.
4. Добавь точный поиск gid и выбор узла. Все идентификаторы — строки.
   Не используй Number/parseInt для gid, в том числе для graph library.
5. Используй готовую лёгкую graph library, если она уже установлена;
   иначе выбери одну подходящую. Не пиши собственный graph engine.
   Если lookup полной карточки для fixture-node отсутствует, покажи
   честный unavailable/empty state, не dossier другого gid.
6. Дай возможность проверить предусмотренные fixtures: обычная карточка,
   изолят, depth=4, урезанное окружение и ENTITY_NOT_FOUND.
   Отображай метку «Учебные данные». Не дополняй 6 fixture-узлов
   выдуманным top-20 и не выдавай их за сеть из исходного кейса.
7. Сделай блоки «Почему роль» и «Почему приоритет». Priority evidence
   определяется по rule_id=priority_v0; вклады не пересчитывай в React.
   Если fixture не содержит вкладов, покажи отсутствие данных, не придумай.
8. Подписи ролей возьми из DECISIONS.md. Для coordinator:
   «Структурный посредник (кандидат)». Priority — баллы, не вероятность
   преступления. Depth=4 объясняет границу наблюдения, не оседание денег.
9. Реализуй loading/error/empty states и вывод количества скрытых соседей.
   Кнопки фильтров не должны создавать иллюзию поиска по полной сети,
   если сейчас доступна только ограниченная fixture-коллекция.
10. Запиши frontend/README.md с фактическими install/dev/build командами
    и точкой будущего подключения API. Сохрани package lockfile.

Проверь build и ручной сценарий: выбрать узел → поменялись граф/карточка;
найти точный gid; открыть изолят; увидеть boundary warning; увидеть
omitted_count; обработать unknown gid. Проверь, что ID нигде не округлён.
Если визуальная проверка недоступна, явно сообщи, не утверждай, что она была.

Не делать: backend, расчёты ролей/priority, второй комплект contracts,
полноценный чат, LLM integration, fancy animations, многостраничный UI.
Готовность backend не должна блокировать этот этап.

После проверок создай локальный commit своей области. Не merge в main
и не force push. В конце: команды запуска, что работает, результаты build
и проверки UI, ограничения fixtures, какие endpoints нужны следующим этапом.
```

## Общий checkpoint после блока

1. Даулет показывает три рассчитанных файла, время выполнения и проблемы правил.
2. Аки показывает рабочий экран и все три состояния узла: обычный, изолят, boundary.
3. Нурасыл показывает проверенную границу tools и не более трёх смысловых замечаний.
4. Команда сверяет types, имена полей и gid:string. Следующий блок — реальный snapshot/API → экран. Общее время планирования не продлевается.

Если CSV ещё не готовы, Нурасыл помогает Даулету закрыть конкретный аналитический blocker; не увеличивает сложность агента. Публикацию feature-веток и интеграцию в main выполняют согласованно после проверки, без force push.
